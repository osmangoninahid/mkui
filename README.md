# mkui

A TUI for your Makefile. Run `mkui` in any repo with a Makefile and get a
searchable, keyboard-driven list of every target, with `##` comments shown as
descriptions.

```
mkui  /Users/you/project/Makefile

▸ build          Compile the binary
  test           Run the test suite
  lint           Run linters
  clean
  main.o

  ↑/↓ move · enter run · / filter · q quit   5/5
```

## Install

```sh
brew install osmangoninahid/tap/mkui
```

Or from source:

```sh
go install github.com/osmangoninahid/mkui@latest
```

## Usage

| Key           | Action                        |
| ------------- | ----------------------------- |
| `↑`/`↓`/`j`/`k` | Move                        |
| `/`           | Filter by name or description |
| `enter`       | Run the selected target       |
| `g` / `G`     | Jump to top / bottom          |
| `q`           | Quit                          |

`mkui --list` prints targets as TSV instead of opening the TUI, so it composes
with other tools:

```sh
mkui --list | fzf | cut -f1 | xargs make
```

## Documenting targets

Any target with a `##` comment gets a description, and sorts to the top:

```make
.PHONY: build
build: ## Compile the binary
	go build ./...
```

## How targets are found

`mkui` runs `make -pRrq` and parses make's own rule database rather than
regexing the Makefile. That means targets from `include`d files and ones
generated by `$(shell ...)` show up correctly, and pattern rules (`%.o`),
special targets (`.PHONY`) and the makefile itself are filtered out.

One consequence: `make -p` evaluates the makefile, so parse-time `$(shell ...)`
calls do execute. Don't point `mkui` at a makefile you don't trust. If `make`
isn't on `PATH`, it falls back to a plain scan of the file.

Known gap: `##` descriptions are only read from the top-level makefile, so a
documented target defined in an `include`d file shows up in the list without
its description. Fixing it means following `include` directives, or reading the
`from '<file>', line N` annotations make already prints in the database.

## Releasing

Tagging triggers GoReleaser, which builds darwin/linux × amd64/arm64 binaries,
attaches them to a GitHub release, and opens a commit on your tap repo.

One-time setup:

1. Create a public repo named `homebrew-tap` under your account.
2. Create a classic PAT with `repo` scope on it.
3. Add it to this repo as the `HOMEBREW_TAP_GITHUB_TOKEN` secret.

Then:

```sh
git tag -a v0.1.0 -m "first release"
git push origin v0.1.0
```

Test the config without publishing first:

```sh
goreleaser release --snapshot --clean
```

## Colors and theming

`mkui` only ever asks for ANSI colors 0-15. Those are *slots* the user's
terminal theme fills in, so the UI inherits Solarized, Gruvbox, Nord or
whatever else is configured, instead of fighting it. Colors 16-255 and hex
values are fixed pixels that ignore the theme entirely, which is how a TUI
ends up with grey-on-grey text for anyone on a light background.

Consequences worth knowing:

- **No background detection.** Because nothing is hardcoded, `mkui` never needs
  to know whether your background is light or dark, so it never sends an OSC 11
  query. That query is a round trip some multiplexers swallow and that can race
  with the input reader.
- **The selected row uses reverse video**, which swaps your own foreground and
  background. It cannot clash with a theme the way a hardcoded highlight can.
- **`NO_COLOR` strips reverse video too**, not just color, so the `▸` cursor
  glyph is what marks the selection in that mode.

Glyphs fall back to ASCII (`>`, `...`, `|`) when the locale is not UTF-8, when
`TERM=linux`, or when `MKUI_ASCII=1` is set.

Because everything degrades through `termenv`, truecolor terminals (iTerm2,
kitty, WezTerm, Alacritty, Terminator, Windows Terminal) and 256-color-only
ones (macOS Terminal.app) receive byte-identical output.

`render_test.go` renders the UI under every color profile so portability
regressions show up in `go test`.

## Demo assets

`demo/demo.tape` and `demo/themes.tape` are [VHS](https://github.com/charmbracelet/vhs)
scripts. They drive the real binary in a real terminal emulator, so the output
is evidence rather than illustration.

```sh
brew install vhs ttyd ffmpeg
go build -o /usr/local/bin/mkui .
vhs demo/demo.tape      # -> demo/mkui.gif
vhs demo/themes.tape    # -> demo/frames/, the same screen in 4 themes
```

`themes.tape` is the portability check: if a color is unreadable on Solarized
Light, it will be unreadable in that render too. Wire it into CI with
`charmbracelet/vhs-action` to catch regressions.
